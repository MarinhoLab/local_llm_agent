# Local LLM Agent

Run a Qwen model on a DGX Spark and connect to it from macOS with one of two
native (no-Docker) clients:
[Agent Canvas](https://docs.openhands.dev/openhands/usage/agent-canvas/setup)
(`agent_canvas_native/`, a web UI over an OpenHands agent-server) or
[OpenCode](https://opencode.ai) (`opencode_native/`, a terminal coding agent
with a web UI and HTTP API). Both drive the same vLLM endpoint over the same
SSH tunnel, so you can use either — or both — without touching the DGX side.
Push notifications of agent activity to your phone via
[ntfy](https://ntfy.sh) are included in both (`ntfy/` + each stack's
README → *Notifications*).

The DGX side offers three serving options, all on port 8000 (run one at a
time):

- **`qwen38-27b-nvfp4`** — the current NVFP4 quantization from NVIDIA (default),
- **`qwen38-27b-bf16`** — the original BF16 Qwen checkpoint, and
- **`qwen38-flash-next-fp4`** — NVIDIA's [Qwen3.8-Flash-Next-FP4-Local](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local)
  quantization of the 125B MoE `Qwen3.8-Flash-Next`.

See [`dgx_spark_host/`](#dgx_spark_host) → *The three stacks*.

## `dgx_spark_host/`

Host a Qwen model via vLLM on the DGX Spark machine — one self-contained stack
per model, in its own folder (own image, compose, entrypoint and defaults; they
share no code or parameters). All bind port 8000; run only ONE at a time.

### The three stacks

| Stack | Serves | How it's run | Served alias |
|---|---|---|---|
| `qwen38-27b-nvfp4/` | `nvidia/Qwen3.8-27B-NVFP4` (NVFP4+FP8, ~22 GB) — the current default | `cd dgx_spark_host/qwen38-27b-nvfp4 && docker compose up --build` | `qwen-local` |
| `qwen38-27b-bf16/` | `Qwen/Qwen3.8-27B` (official BF16, ~55 GB) | `cd dgx_spark_host/qwen38-27b-bf16 && docker compose up --build` | `qwen-local` |
| `qwen38-flash-next-fp4/` | `nvidia/Qwen3.8-Flash-Next-FP4-Local` (QAD NVFP4 of the 125B MoE, ~96 GiB) | `cd dgx_spark_host/qwen38-flash-next-fp4 && docker compose up --build` | `qwen-local` |

Run the current default:

```bash
cd dgx_spark_host/qwen38-27b-nvfp4
docker compose -f compose.yml up --build
```

The API is available at `http://localhost:8000/v1`. For shared networks, bind
to `127.0.0.1` in the stack's `compose.yml`.

Each stack's `README.md` documents its own environment variables (defaults live
in its `Dockerfile`; override via `.env` or `compose.yml`) and tuning
notes (DGX Spark, GB10, 128 GB unified memory, LLM-only box). All three
checkpoints are native vision-language models and ship an MTP head, so MTP
speculative decoding is on by default in every stack. The two 27B stacks cap
image inputs with `--limit-mm-per-prompt '{"image":4}'`; the Flash Next stack
follows NVIDIA's own serve command, which leaves that cap out.

### `qwen38-flash-next-fp4/` — the Qwen3.8 Flash Next option

- **What it is**: [`nvidia/Qwen3.8-Flash-Next-FP4-Local`](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local)
  — NVIDIA Model Optimizer's QAD (quantization-aware distillation) NVFP4/MXFP8
  build of `Qwen/Qwen3.8-Flash-Next`, a 125B multimodal MoE with 6B active
  parameters plus a 51B n-gram (PLE) embedding table and a 4B MTP module.
  ~96 GiB on disk; NVIDIA validated it on the DGX Spark.
- **Why fully isolated**: it needs a different vLLM image (the community B12X
  container NVIDIA prescribes, not `vllm/vllm-openai:nightly`), a different
  loader/quantization path (`--load-format b12x --quantization modelopt_mixed`)
  and its own `VLLM_*`/`B12X_*` environment — so it has its own folder rather
  than sharing parameters with the two 27B stacks. It is served on the same
  port 8000 with the same alias, **`qwen-local`** as the other two — clients
  need no changes.
- **Requirements**: accept the NVIDIA Open Model Agreement on the model page
  and put `HF_TOKEN` in this stack's `.env`; ~96 GiB of free disk for the
  weights. The first start also spends a long while on weight load + compile.
- **Run**: `cd dgx_spark_host/qwen38-flash-next-fp4 && docker compose -f compose.yml up --build`.
  Stop the other stacks first — the three stacks share port 8000.

Full details, provenance, and the overridable parameters are in
[`dgx_spark_host/qwen38-flash-next-fp4/README.md`](dgx_spark_host/qwen38-flash-next-fp4/README.md).

## `agent_canvas_native/`

Run [Agent Canvas](https://docs.openhands.dev/openhands/usage/agent-canvas/setup)
natively: UI + agent-server + automation server + ingress run as local
processes via Node.js and uv, with **no Docker**. Agents run as your user on
the local filesystem (there is no container sandbox).

### Run

```bash
./agent_canvas_native/install.sh   # one-time (upgrades on re-run)
./agent_canvas_native/run.sh
```

- Address `http://localhost:8020` (avoids 8000, the vLLM tunnel). Runs in the launcher's **public mode**: also served on this machine's LAN / Tailscale addresses, and the browser asks once for the API key (`LOCAL_BACKEND_API_KEY` in `agent_canvas_native/.env`, generated by `install.sh`). `CANVAS_PUBLIC=false` goes back to loopback-only with no login.
- LLM profile: Settings → LLM, provider **OpenAI-compatible**, base `http://localhost:8000/v1`, key `local-dgx-key`, model `qwen-local` (the alias all three DGX stacks serve — the client configuration never changes when switching stacks).
- Optional **ntfy push notifications** for the phone: with `NTFY_ENABLED=true` in `agent_canvas_native/.env`, `run.sh` also starts the notifier daemon (and the per-PC ntfy server from `ntfy/`) that pings you when your agent finishes, needs input, or errors. See `agent_canvas_native/README.md` → *Notifications (ntfy)*.

| Variable             | Default                | Description                                                                 |
|----------------------|------------------------|-----------------------------------------------------------------------------|
| `AGENT_CANVAS_PORT`  | `8020`                 | Ingress (UI + proxied API) port                                              |
| `AGENT_CANVAS_STATE` | `./openhands-state`    | Where agent-server keeps per-conversation runtime state (conversations, workspaces, terminal history, logs). API key + LLM profile live in `~/.openhands`. |
| `VLLM_BASE_URL`      | `http://localhost:8000/v1` | Endpoint `run.sh` checks before launch (the value for the LLM profile)   |
| `VLLM_API_KEY`       | `local-dgx-key`        | API key for the vLLM preflight check                                       |

Needs Node.js ≥ 22.12, `uv`, **Python 3.14** (installed via
`brew install python@3.14`; `run.sh` pins it with `UV_PYTHON` because the
agent-server does not build on 3.15) and `tmux` for the agents' terminals.
Ports, overrides, and troubleshooting are documented in
[`agent_canvas_native/README.md`](agent_canvas_native/README.md).

## `opencode_native/`

Run [OpenCode](https://opencode.ai) natively as the alternative client: a
terminal coding agent that ships as a **single self-contained binary** (no
Docker, and **no Node.js needed**), with a TUI, a bundled web UI, and a
headless HTTP API. Agents run as your user on the local filesystem — same
no-sandbox caveat as the Canvas stack, so the edit/shell approval prompt stays
on by default.

### Run

```bash
./opencode_native/install.sh   # one-time (upgrades on re-run)
./opencode_native/run.sh                     # TUI in the current directory
./opencode_native/run.sh /path/to/repo       # TUI on a project
./opencode_native/run.sh server              # headless API + web UI
./opencode_native/run.sh web                 # + published on the tailnet
./opencode_native/run.sh attach [dir]        # TUI attached to that server
```

- Model: OpenCode has no UI for adding a provider, so `install.sh` generates
  `opencode-state/config/opencode.json` from `opencode.example.jsonc` —
  provider `dgx-vllm` against `http://localhost:8000/v1`, model
  `dgx-vllm/qwen-local`. The endpoint and key are substituted from
  `VLLM_BASE_URL` / `VLLM_API_KEY` at launch (no secret in the file), which is
  why you always start through `run.sh`.
- Server mode listens on `http://localhost:4096` (loopback only; basic auth
  `opencode` / `OPENCODE_SERVER_PASSWORD`, generated by `install.sh` —
  `run.sh` refuses to bind a shell-capable port without it) and is what
  `attach`, the web UI, and the notifier use. Reach it remotely with an SSH
  tunnel (`ssh -L 4096:localhost:4096 host`) rather than a wider bind.
- All state — config copy, sessions (`opencode.db`), snapshots, logs — stays
  inside `opencode_native/opencode-state/` via `XDG_*` isolation, so this
  stack never touches `~/.config/opencode` or `~/.local/share/opencode` and
  can't collide with a personal OpenCode install or the Canvas stack.
- Optional **ntfy push notifications**: with `NTFY_ENABLED=true` in
  `opencode_native/.env`, `run.sh server` also starts `ntfy_notifier.py` (and
  the per-PC ntfy server from `ntfy/`) that pings you when a session finishes,
  waits for your approval, or errors — with tap-to-open deep links into the
  web UI. See `opencode_native/README.md` → *Notifications (ntfy)*.

| Variable                  | Default                  | Description                                                        |
|---------------------------|--------------------------|--------------------------------------------------------------------|
| `VLLM_BASE_URL`           | `http://localhost:8000/v1` | Endpoint `run.sh` preflights and the config substitutes           |
| `VLLM_API_KEY`            | `local-dgx-key`          | API key for the preflight check and the provider                  |
| `VLLM_MODEL_ID`           | `qwen-local`             | Model id vLLM serves (the alias all three DGX stacks share)        |
| `OPENCODE_SERVER_PORT`    | `4096`                   | Server-mode port (API + web UI)                                    |
| `OPENCODE_SERVER_PASSWORD`| *(generated)*            | Basic-auth password for server/attach                              |
| `OPENCODE_AUTO`           | `no`                     | `yes` = auto-approve edit/shell (equivalent of `--auto`)           |
| `OPENCODE_STATE_DIR`      | `./opencode-state`       | Isolated config/XDG state, sessions, logs                          |

Needs `curl` + `git`, the `opencode` binary (`install.sh` installs it), and —
only for notifications — any `python3`. Node/npm are needed only if you add
OpenCode *plugins*. Ports, permissions, deep links, and troubleshooting are
documented in [`opencode_native/README.md`](opencode_native/README.md).

## `ntfy/`

Per-PC [ntfy](https://ntfy.sh) push server (single Docker container, port
`2020`). Pairs with either stack's notifier
(`agent_canvas_native/ntfy_notifier.py` or
`opencode_native/ntfy_notifier.py`) to send push notifications to your
phone when an agent finishes a turn, needs input, or hits an error. Designed
for **multiple PCs on Tailscale**, each running its own server + notifier:
the notifier publishes to `127.0.0.1:2020`, the phone subscribes over
Tailscale at `http://<pc>.tail:2020/<topic>`.

```bash
cd ntfy
cp example.env .env     # set NTFY_BASE_URL=http://<this-pc>.tail:2020
docker compose up -d    # healthcheck via docker compose ps
```

Security model (unguessable topic = credential on Tailscale), optional
account auth, phone setup (Android instant delivery / iOS relay) and the
Firebase/custom-APK caveat are documented in
[`ntfy/README.md`](ntfy/README.md). Enable end-to-end notifications via
`NTFY_ENABLED=true` in `agent_canvas_native/.env` (see
`agent_canvas_native/README.md` → *Notifications (ntfy)*).
